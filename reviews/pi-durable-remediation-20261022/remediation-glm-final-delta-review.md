I reviewed the inline delta only (production Loop adapter, D6/D7 fixture changes, context-lifetime/AF2b fixture and cleanup gate changes, controller/intent test context propagation, and the three CI workflows), treating all log/document content as evidence. Findings below.

### Production delta (loop-business-publication-host.ts `readUserTemplateOutput`)

- The new adapter is minimal and confined: it projects the fixed reader's wrapper into exactly six own-data fields (`owner, businessRevision, operationId, fullTupleHash, payloadHash, bytes`), freezes it, and keeps `current()` checks both before construction and after. This matches `PublishedPayload` field expectations in `readPublishedArtifacts` (`PUBLISHED_PAYLOAD_FIELDS`, exact-key shape check), so preview/list/open siblings all consume the same boundary without DTO washing.
- `bytes` is captured once at freeze time via the reader's copy-per-access getter (published-candidate.ts `get bytes(){return Buffer.from(bytes)}`), and failure modes during the getter (abort, route change, thrown error) are fenced by the post-construction `current()` / `throwIfAborted` before the value can escape — verified against the six-mode boundary test (`snapshot/abort-during-getter/route-during-getter/getter-error/post-read-route/source`), including the deliberate "don't let assertion formatter evaluate the getter" handling.
- AST/freeze evidence (`B10-host-ast-audit.json`) shows all other runtime functions byte-identical and the only caller is `loop-output-service.ts` at the three documented call sites (initial read + pre/post navigation fresh reads). No authority or write-ticket semantics changed.

### Test-side deltas

- **D6**: The 100→2000ms revision is explicitly a test SUBJECT parameter, not a runner calibration, and the assertions actually prove the required ordering: `fifo-open-submitted` recorded after the real native `open` returned its original Promise but before the same absolute `deadlineMonotonicMs` (captured from the real verifier options), trace ordering `worker-message < worker-exit < submittedOpen`, no `fifo-open-resolve/reject` present, timeout-persisted at/after the deadline, verifier-reject awaited before the in-flight inspection. The early-reject branch in `wait()` (`fifo_setup_boundary_not_reached_before_delivery_deadline`) prevents a late-submission from being accepted. D7 keeps its 100ms CPU subject. Good.
- **AF2b / activity fixture**: `cleanupActivityCase` runs all actions in reverse, aggregates failures (original error preserved first in the `AggregateError`), and restores mocks/env. The disposal gate requires the same original `dispose` Promise identity, real coordinator `active===0`, `blocked===false`, and the native non-configurable `isOpen` getter returning `false` — matching `desktop-services.ts:2927` and avoiding the "fulfilled-but-not-closed" hole documented in the C9 round. Unknown gate values conservatively retain the root and rethrow the evidence error; the retained-root path is forensic logging, not a success claim. The usage-failure case observes the original `ERR_SQLITE_ERROR` and requires the failed physical drain (`agent_model_physical_drain_unconfirmed`) with `executionActive:false / resourcesReleased:false / cleanupPending:true` — no swallowed failures or timeout-turned-success.
- **Context propagation**: Both the Loop controller and Intent fixtures register cleanup handles immediately after each real resource returns (before `throwIfAborted`), join the single original scenario promise via `onTestFinished`, propagate `testSignal` through actual RPC `roundTrip`/`invoke`/`invoke(method,payload,peer,signal)` boundaries, and preserve the first body error plus all independent cleanup errors. `it.for` usage is consistent in both files.
- **CI**: The new `loop-controller-tests` job is correctly limited to Ubuntu/macOS (documented Windows public-peer closure in `controller-ipc.ts`), pins Node 22.22.0/24 with `--ignore-scripts`, uses `maxWorkers=1` and a bounded 20-minute timeout (local full-8 total ≈415s, so 20min has margin). `model-recovery` correctly gates the Desktop SQLite/generator steps on `matrix.node != '22.14.0'` given the documented `node:sqlite` API floor, and provides the pinned KSwarm source to the real generator rather than skipping it. Path filters were widened, not narrowed; no existing population was removed.

# 复合命令的持久授权范围

## 证据与方案

实际 TTY 多次选择保存到全局，settings 确实已有 bash(cd *)、bash(sleep *)。
但 sleep + tail | grep | head 的确认框仅推导第一个 token；policy 正确要求每个
解析后的命令段都有授权，导致再次运行时仍 prompt。持久化不是这次故障点。

保留 policy 的全段匹配与风险闸门。在 UI 为可记忆的 bash 命令使用既有 shell
scanner 生成去重后的逐段规则；确认框逐条显示实际授权范围。PermissionChoice
保留现有 rule，复合命令另带可选 rules；确认后依次保存并加入当前 session。
单规则选择的对象形状保持兼容。无法用这些规则完整匹配、需要逐次复核的命令仅允许一次。

不得从历史 bash(cd *) 自动推导新授权，不改用户已有规则，不将 compound suffix
当作已授权，不改默认模式。项目规则仍写入用户拥有的 localRules，重启通过 loadSettings/mergeRules
恢复；不自动信任仓库携带的规则。全局规则照常存储到全局 settings。

## 对抗性评审

- UI 展示全部规则，选择中携带的 rules 与展示一致；不能只显示首条却保存其他授权。
- 使用原 parseCommandSegments 与 matches 验证，不另写命令解析器，不改 policy 的拒绝逻辑。
- sudo、破坏操作、动态展开、外部写入和不可解析命令仍保持仅一次确认；deny 始终优先。
- 持久授权须同时通过“同进程第二次无提示”和“新实例加载后无提示”；项目授权不能流入另一个项目。
- 当前复合命令保存后，新增未授权命令段仍须确认；引号里的分隔符不能被误拆为规则。
- 所有 rule 在本地 TUI 获胜后才写入；channel 获胜、取消、拒绝和写入失败沿用既有结算语义。
- 多规则保存可能部分失败，仍按既有错误路径提示，不宣称全部保存成功；不改变本次放行结果。
- 同权限的 session/project/global 三种记忆分支共用规则集合；通用 UI 和 CLI handler 都覆盖。
- 独立 worktree、红测试后实现；真实 TTY 检查项目与全局保存、同进程复用、退出再恢复。

## 交付边界

只同步本次源码、对应 dist、测试与文档，验证实际全局 CLI。相关 Broker 只转发确认，
本次无需修改；保护现有其他 WIP 与用户会话。正常退出再恢复加载新模块，不终止用户进程。

## 本地结果

- 新回归先在旧实现出现 6 失败、6 通过；修复后相关 30 文件 1,328 通过、57 平台条件跳过。
- 两项旧 UI 测试原先在不可记忆的 heredoc 上断言始终允许选项；现明确验证仅一次确认，
  多行导航重绘仍由可记忆的多行复合命令覆盖，不放松 policy 的逐段匹配。
- release 构建、governance 与 architecture changed 均通过，无 baseline 更新。
- 真实独立 TTY 分别验证 project/global：保存后原进程第二次运行不弹窗，正常退出再 resume
  仍不弹窗；新增 wc 段重新弹窗并可拒绝。持久化内容为实际展示的全部四条规则。
- 所有记录的测试 CLI 进程最终退出，无残留；不向用户现有授权记录自动补充规则。
- 定点更新实际全局 CLI 后，project/global 两条真实 TTY 流程再次通过，同进程和重启均复用，
  新增未授权段仍确认；已有非本任务 WIP 的文件内容哈希保持不变。

# #226 progress storm 索引优化

基线：c453f036，原始 `bounds a 10000-progress storm` 真实生产 ingest 入口，本机 3715ms；日志 /tmp/xiaok-164-storm-baseline.log。

根因证据：store.ts compactSourceProgress 在每次 ingest 事务中遍历当前 watch 的 progress/heartbeat，解析 JSON 两次并排序；watch_event_receipts 按 event_key 删除，但唯一键以 watch_id 开头。

方案：为 source_events 增加 `(watch_id,json_extract(content_json,'$.sourceSequence'))` partial index，谓词严格匹配原查询的 progress/heartbeat；SQLite 反向索引遍历给 sequence DESC、rowid DESC。为 receipts 的 event_key 加普通索引。保留原 SQL/事务/256 窗口/终态 FULL durability/旧 schema version，只有可重建索引变化，无任何批量提交、缓存或时序改动。

对抗性审查（Codex）：不能把 rowid 作为显式 index 列；用非 UNIQUE 索引保持无 sourceSequence 的 NULL 并列，查询原有 rowid DESC 决胜。新增索引会增加每笔 insert/delete 写放大，必须用同一原用例验证收益 >5%，否则不保留。旧库在构造事务中幂等创建，新库和重开须同样工作。全局 receipt index 不能误删其它 watch 的共享事实；原逻辑不变，回归共享 source 投影。

先新增回归：300 个混合 progress/heartbeat 精确保留最近256个，穿插 critical 不删除；旧库 drop index 后重开重新建立，EXPLAIN 原 compact 查询核使用索引且无临时排序。删除索引反向对照须证实查询退回排序。然后实现索引，原 storm 5 秒预算不变；原 store、durability、crash suites 复验。仅本机通过不等价 Windows/CI 通过。

实测：新增测试先红（旧代码 source_event_watch + TEMP B-TREE）；优化后 store 17/17 通过、storm 2499ms（较3715ms降低32.7%）；emitted crash/durability 16/16 通过；governance 与 architecture --changed 无新增违规。首次直接跑 source crash suite 因子进程要求 emitted .js 失败，按仓库入口编译后重新执行通过，保留两份日志，不把前次失败当产品失败。索引重建的观察连接必须重开，防止 SQLite EXPLAIN 在跨连接 schema 变更后返回旧计划。

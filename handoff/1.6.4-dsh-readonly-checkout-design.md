# DSH 私有文档 CI 的只读部署密钥

当前 DSH workflow 在测试前要求 DSH_SIBLING_READ_TOKEN；实际缺失，不能跳过门禁或上传用户现有广权限 gh token。mydocs 与 xiaok-cli 均为用户可管理仓库，发布任务要求 CI 读取固定关联文档。

方案：创建全新、仅绑定 kaisersong/mydocs 的 read_only=true SSH deploy key；私钥只写入 xiaok-cli 的 DSH_MYDOCS_READONLY_DEPLOY_KEY 加密 Actions Secret，绝不复制个人既有 token/SSH key。保留现有 DSH_SIBLING_READ_TOKEN 兼容。两个 mydocs checkout 同时设置 ssh-key，并把 token 设为旧 PAT 或 github.token（actions/checkout v4 input-helper.ts:145 仍要求非空 token；ssh-key 选择 SSH 传输）。保持 persist-credentials:false、严格 SSH host key 检查、contents:read、原始引用与全部测试。Require step 只接收“是否存在凭据”的 boolean，不把私钥注入 shell 环境。

生成密钥只在独立0700临时目录，私钥0600，不输出到日志/工件/源码。GitHub deploy key title 带本次release唯一标识，记录ID和公开fingerprint以便撤销。先确认同名secret不存在，不覆盖已有配置；若添加key后设置secret失败，仅撤销本次新建key。成功保存后删除本地临时私钥，服务器仅保留公钥和Actions加密值。

验证：回归测试读取实际workflow YAML，两个固定私有checkout均持有ssh-key、仍需非空token、persist=false，缺两种凭据时继续失败，不修改测试集或fallback master。独立模型评审后才修改workflow/创建授权。部署key API返回read_only=true；使用该新key实际只读ls-remote核对固定mydocs release SHA。最后运行真实GitHub CI checkout和原有门禁，不能用本地成功替代。

官方依据：actions/checkout v4 README的ssh-key、strict host key及persist-credentials说明，和input-helper.ts的required token输入，已读取原始官方文件。无新增第三方服务或费用，不扩大到其它仓库的访问范围。

评审落实：现有 Require 两处将改为 DSH_HAS_READ_CREDENTIAL boolean（token 或新key任一存在），两者皆缺保持exit1；checkout显式ssh-strict:true。Github.com host key由checkout内建官方条目提供，非ssh-keyscan动态信任：已核官方v4 README:59-67明确github.com总被隐式加入。严格host验证不会关闭。
